# 竞品对比测量规范

> 这份规范的每一条都来自 2026-09 那轮 ctxmux vs tmux 全量对比里**真实犯过的错**。
> 不是通用最佳实践的转述 —— 每条都附着当时那个具体的错法, 因为脱离了案例, 规则
> 读起来都像常识, 而常识恰恰是当时没挡住它们的东西。
>
> 案例出处: `.bagakit/feature-tracker/features/f-22aczwza9/artifacts/OPINIONS_002.stop_latency_misattribution.md`

## 一、表的形状

对比宽表用这十列, 顺序固定:

```
| 优先级 | # | 维度 | 这一维在测什么 | 什么时候真的咬人 | 子维度指标 | 我方 | 对手 | 比值 | 判定 |
```

每列存在的理由:

| 列 | 为什么非要有 |
|---|---|
| **优先级** | 没有它, 读者会把 13 个维度当成同等重要, 于是去优化绝对值 0.02 秒的那个 |
| **维度** | 一句话的名字。它是索引, 不是解释 |
| **这一维在测什么** | 用**大白话**说, 不能用缩写和内部术语。见 §1.1 |
| **什么时候真的咬人** | 优先级是判断, 这一列是**让判断可被反驳的证据**。见 §1.2 |
| **子维度指标** | 一个维度往往有基线 / 边际 / 各档位多个数, 摊开列, 不合并 |
| **我方 / 对手** | 实测值, 带单位 |
| **比值** | 一律 我方/对手。能力差异这里写 `—` |
| **判定** | 独立成列, 不要混在比值里。见 §1.3 |

### 1.1 "在测什么"要说人话

写给一个没参与过这轮测量的人看。判据: **把这一列单独抽出来, 他能不能明白这行在比什么。**

```
✗ "边际内存 / 单元"                      — 缩写, 且没说为什么要关心
✗ "stop 路径 members() 的 census 开销"   — 内部实现术语泄漏到对比表
✓ "多开一个会话, 内存涨多少"
✓ "程序吐出去的字节, 还能不能一个不差地读回来"
```

### 1.2 "什么时候咬人"必须可反驳

这一列不是补充说明, 它是**优先级那一列的依据**。写成可以被打脸的具体条件:

```
✗ "规模大的时候会有影响"                  — 没有任何人能反驳这句话
✓ "句柄配额有限。默认 1024 的机器, 我们几百个会话就开不动了"
✓ "不咬人 —— 四千个会话全空闲, 我们低到测不出来"
```

第二个例子值得注意: **判 🟢 低也要给依据。** "这条不重要"同样是判断。

### 1.3 判定与比值分列

比值是测量, 判定是结论, 混在一格里会让人以为结论是算出来的。

判定只用这几个值: `✅ 赢` / `❌ 输` / `持平` / `能力差异` / `语义差异`。

## 二、能力差异不出倍率

**一个做不到某件事的系统, 不是"慢了无穷倍"。**

这轮里 tmux 在四个维度上根本没有对应物 (进程结束后重放、按字节游标重放、崩溃恢复、
舰队级保留预算)。这些行:

- 比值列写 `—`
- 判定列写 `能力差异`
- 我方/对手列写**实测到的原始值**, 不要写 "∞" 或 "不支持"

```
| 崩溃恢复 | ... | SIGTERM 后恢复 | 1000/1000 | 1 | — | 能力差异 |
```

那个 `1` 是 tmux 重启后的新空会话, 不是"恢复了 1 个"。它也**不是失分** —— tmux 从
未承诺活过自己的进程。把设计选择记成失败, 对比就失去了可信度。

另有一类是 **语义差异**: 两边都有数, 但衡量的不是同一件事。例: 我们的 `stop` +
`remove` 才等于 tmux 的 `kill-session`; 我们保留原始字节流而 tmux 保留渲染后的网格。
这种要在表下注明对齐关系, 逐动词的拆分只用于定位缺陷在哪一步。

## 三、公平性: 对齐实际保留的东西, 不是配置项

tmux 默认 2000 行 history 会让它显得比真实情况差。**拿我方优势去比对手的最差默认
配置, 等于自己给自己注水。**

这轮的做法: 同时给出"等保留量"和"等深度"两组, 并明确**引用哪一组**。

```
| 同样存 799 MiB   | 17.93% | 41.1% | 2.29x | ✅ 赢 ← 引用这个 |
| 同样深度 (4096)  | 0.0224 | 0.1355| 6.04x | ✅ (高估, 不引用) |
```

**主动标注哪个数字高估了自己。** 一份只挑对自己有利口径的对比, 读者迟早会发现, 那
时候所有数字都不可信了。

## 四、两边必须同批次、同宽限期

### 4.1 同批次

只重跑自己这一臂, 拿新数据比对手的旧数据 —— 主机负载已经变了, 比的是两个时刻而不
是两个系统。

**这轮的实例**: 修复 stop 后重跑, 我写的 `run-fixed.sh` 导出了 `BIN_DIR` 却漏掉
`TMUX_BIN`, 而 tmux 不在该机 PATH 上, 三个 cell 的 tmux 臂全部吐 `{"error":"no_server"}`。
那不是 tmux 的结果, 是我的脚本 bug。**作废重跑, 而不是只补缺的那一半。**

重跑后 tmux 两轮 25.33 s / 25.36 s, 差 0.1% —— 这个一致性本身就是"主机状态可比"的
证据, 值得写进报告。

### 4.2 同宽限期 ← 最隐蔽的一种

**这轮的实例** (`paired-head.sh`):

```bash
# 我方: 停完之后轮询等排空, 最多 30 秒
for _ in $(seq 1 150); do [ "$(pgrep -P "$pid" | wc -l)" -eq 0 ] && break; sleep 0.2; done
leftover=$(pgrep -P "$pid" | wc -l)

# 对手: kill-server 之后只 sleep 2 秒就数
tmux -L "$L" kill-server; sleep 2
leftover=$(pgrep -P "$pid" | wc -l)
```

结果 tmux 在 2048 / 4000 两档"残留 100% 子进程", 看上去是重大缺陷。真相是杀几千个
进程两秒不够 —— **128 / 512 档都是 0 正好证明这点**: 小舰队两秒够用。

这条数据被**拒绝出具**, 而不是打个折扣写进表。

> **通则**: 任何等待、超时、重试、轮询上限, 两边必须相同。不同的宽限期会让慢的那
> 一边看起来像是漏了东西, 而这种缺陷长得和真缺陷一模一样。

## 五、归因: 先问自变量和什么共线

**这是这轮最贵的一课 —— 同一个错误犯了五次。**

`stop` 延迟按舰队大小 N 拟合, 得到 `116.00 + 0.0816·N`, R² = 0.999。于是去找"遍历
舰队的代码"。真凶却是它扫描**整台机器**的 `/proc`。

原因: 实验里**每个会话恰好新增一个子进程**, 所以舰队大小 N 与主机进程总数 P 完全
共线。两个解释预测**完全相同的曲线**, 再多档位、再高的 R² 都分不开。

> **共线的自变量不能做归因。** 问题不在数据量, 在实验设计。

### 5.1 判别实验: 让两个解释预测不同的东西

```
把舰队钉死在 1 个会话, 只改变机器上与我们无关的外来进程数。
  · 若是"舰队扫描" → 外来进程不应有任何影响
  · 若是"全机扫描" → 外来进程照样拖慢我们
```

结果 121 ms → 352.7 ms。**一次运行, 两分钟, 决定性。**

同一个探针顺带排除了持久化层 (带/不带 `--state-dir` 无差别), 并保留 `start`/`remove`
作为对照组 —— 它们全程不随进程数动, 坐实了代价专属 stop 路径。

### 5.2 算术对得上 ≠ 机制对了

- `116 / 10 ≈ 12 个轮询间隔` —— 凑上了, 错的
- 修复后剩 20.7 ms, `20.7 ≈ 2 × 10 ms` —— **又凑上了, 又是错的**

第二次尤其危险, 因为它听起来像"修掉真凶之后我原先的解释终于成立了"。扣掉客户端
成本才看清: daemon 侧只有 5.4 ms, 与兄弟动作同级; 20.7 里有 15.6 ms 是**两次客户端
往返**。

> 一个数字凑得上, 只说明它**没被排除**, 不说明它被证实。

### 5.3 不要把错误前提外包给 agent

我让五个 agent 并行去找 "fleet scan", 它们独立得出了同一个结论 —— 因为**那个结论的
边界是我在 prompt 里给定的**。判别实验必须自己设计。

## 六、"过于整齐"是缺陷信号

在共享主机上, 下面这些都该先怀疑测量, 再怀疑系统:

- 每一档的 median 和 p90 **精确相等到小数点后两位** ← 这轮的实例: `ms_between` 没有
  结尾换行, 60 个样本被 `>>` 拼成了一行, 每个分位数都返回同一个数
- 拟合 R² 高得异常
- 比值恰好是整数

## 七、数据出具的三条硬规矩

1. **作废就是作废, 不打折扣。** 口径不对的数据不能"标注一下再用"。这轮拒绝出具了
   `teardown_leftover` 整项。
2. **修前修后不要混在汇总表里。** 汇总表只给**当前状态**; 修复前的数字和推翻过程另
   立章节。混在一起时, 读者一定会把某个旧数字当现状 —— 这轮审计确认了 8 处, 其中
   一处判定还是反的 (冷启动占比修后从"拖累对手"变成"拖累我方")。
3. **只重跑一部分时, 检查那批 cell 顺带产出的其它数字。** 这轮只重跑了 stop 相关
   cell, 但同一批 cell 里的 `start` / `remove` / 冷启动数字也变了, 增量更新时全漏了。

---

## 八、报告要留下三样东西

1. **被推翻的结论**, 连同推翻它的数据。错误归因的过程往往比结论本身更有价值。
2. **被作废的数据**, 连同作废的理由。
3. **测量缺陷清单**。这轮记了七条, 它们有同一个签名: **唯一的诊断信息本来会被当成
   数据。** 一个报 `no_server` 的 cell、一个"残留 4000 个进程"的 cell, 长得都和真实
   测量结果一模一样。

出具对比表之前逐条过:

- [ ] 能力差异行: 比值为 `—`, 未写成倍率
- [ ] 语义差异已在表下注明对齐关系
