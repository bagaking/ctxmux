# Run benchmark and grounding standard

The goal is useful, reliable Run capacity. A terminal is a view; a Run remains
owned and identifiable when that view leaves. A higher score obtained by losing
bytes, narrowing accepted workloads, weakening durability, or concealing failed
input is a regression. This standard owns benchmark claims; the
[comparison conventions](benchmark-comparison-conventions.md) additionally own
competitor comparisons. The [protocol](protocol.md) owns product semantics.

## What a result must establish

| Dimension                  | Measurements                                                                                                    | Independent behavioral evidence                                                                                    |
| -------------------------- | --------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------ |
| Correctness and fidelity   | Offered, PTY-applied, observed, verified and durable bytes; gaps and truncation separately                      | Independently generated bytes, exact half-open cursors, hashes, Run/Runtime/child identity, and ordered replay     |
| Availability and isolation | Attempted/completed/failed/unknown operations, owner and Run service facts                                      | A second real Run continues serving while one writer, client, parser or storage path fails                         |
| Input settlement           | Accepted and rejected receipts, exact confirmed prefix, unknown result count, recovery cost                     | Same operation key retries without duplicate application; transport loss never becomes a zero-byte receipt         |
| Throughput                 | Offered rate, verified payload bytes per second, completion rate and backlog                                    | Receiver verifies bytes; producer counters alone do not establish delivery                                         |
| Latency and fairness       | Start, first output, input/output, controls, page walk, replay, exit/drain and cleanup; per-Run distributions   | Planned/send/completion times; sparse probes alongside floods; missed schedules remain in the record               |
| Resource cost              | CPU time, wall time, utilization, RSS/PSS where available, fds, threads, child/generator costs, storage and I/O | Actual process ownership and host constraints; signed baseline deltas; sampler coverage and cost                   |
| Capacity and pressure      | Offered/admitted/live/terminal/removed Runs, clients, output shapes, saturation knees, precise admission error  | Resource-funded scale beyond qualification sizes, existing Run service after refusal, explicit pressure/truncation |
| Recovery and retention     | Live upgrade interruption, replay/recovery bytes and latency, identities, cold state, churn/leaks               | Planned exec preserves original live children; cold replacement recovers the declared historical class only        |
| Usability                  | Real CLI/SDK attach, input, Ctrl+C, disconnect/rejoin, error and recovery                                       | Public clients exercise the public boundary; mocks and type declarations do not qualify these paths                |

Keep independent dimensions visible. Verified bytes remain measurable after a
gap; the gap and any unrecovered bytes remain correctness failures. A missing
non-output observation is not evidence of lost output bytes. Faster completion
can increase instantaneous CPU utilization while reducing total CPU cost.
Logical queue funding is not RSS. Publish both rather than substitute one.

## Workload and fault matrix

Publish the selected matrix **before execution**, including repetitions,
deadlines, offered rates, payload seeds, retention policy and held-out shapes.
Every selected cell ends in a recorded success, failure, blocked precondition or
unknown outcome. Missing cells cannot be called covered. Keep failed attempts
when correcting a harness. Completion of a benchmark campaign does not imply
that its product qualification passed.

The baseline covers memory-only and persistent native Runs at 128, 512, 2048 and
4000, with idle, all-active and asymmetric mixed phases. These are observation
points, not a product population ceiling. Include a separately named default
policy frontier above 4000 where host resources fund it. If a resource limit
prevents a tier, report that limit and preserve the intended tier. Do not shrink
the target to produce a passing result. Explicit operator-cap refusal and
default-policy capacity are different experiments.

Exercise at least these complementary shapes and failures:

- binary bursts, sparse request/reply, paced token-like fragments, ANSI TUI
  sequences, wide/combining characters and resize while output is active;
- fan-out of 1/8/32 clients, two independent Runs and two independent clients,
  slow and disconnected readers, rejoin from the last verified byte;
- a blocked input writer next to a healthy Run, receipt/result loss, Ctrl+C,
  failed/partial/unknown input, Run-local derived-view faults and shared owner
  failure with truthful availability;
- save/restore cursor after shrinking both rows and columns, including a
  one-row terminal and pending wrap; original raw bytes survive a derived error;
- paged enumeration, start/fork/stop/remove churn, process-tree cleanup and
  bounded-resource refusal without disturbing already accepted Runs;
- planned exec with original children and control/replay continuity, cold
  historical recovery, storage pressure and incomplete/corrupt state;
- a continuous soak with repeated probes and resource trajectories, not only
  a sleeping fleet or one before/after RSS observation.

Population, active fraction, clients and output rate are separate axes. A full
Cartesian product is not required by default: state which interactions the
selected covering matrix exercises and which remain unqualified. A synthetic
token stream is a transport workload, not an actual Agent benchmark. Real
consumer/provider acceptance remains separately named. Level B, imported tmux,
remote endpoints, cross-generation handoff and host-reboot/crash-time PTY
adoption are never inferred from native Level A tests.

## Measurement rules

Record every attempted operation, its outcome and monotonic timestamps. A
timeout is a right-censored observation (completion took at least the observed
wait), not an exact completion latency. Successful-request quantiles are
explicitly conditional on success and accompanied by attempted, successful,
failed and censored counts. Report nearest-rank **sample** quantiles with n,
rank and maximum; a small-sample p99 may equal the maximum and does not establish
a population p99. There is no unexplained minimum sample count. State the
confidence method and its assumptions before making a statistical claim.

Use both closed-loop concurrency and an independently scheduled open-loop
probe when assessing overload. Record intended schedule, actual send delay,
in-flight requests and completions. Do not fabricate unsent requests or
histogram corrections as actual observations. Closed-loop self-throttling is a
different workload, as demonstrated by [Open Versus Closed (NSDI)](https://www.usenix.org/conference/nsdi-06/open-versus-closed-cautionary-tale).

Separate fresh protocol connections, attachment controls, CLI process startup,
SDK dispatch and fixture application response. All are legitimate costs. Do
not remove a real client cost to claim better end-to-end latency. Record warm-up
separately, raw repetitions, ordering and variance; never average percentiles or
discard inconvenient outliers. [Google Benchmark](https://github.com/google/benchmark/blob/main/docs/user_guide.md)
describes repetitions and variance; it does not provide ctxmux SLAs.

Budgets require a user contract or an explicitly frozen regression reference,
with units, scope and derivation. Test deadlines are observation windows, not
latency SLAs. Existing frozen budgets remain intact. New observational baselines
must not become passing regression gates by multiplying their worst result by
an unexplained factor. Do not adopt borrowed limits such as “10 ms”, “2x” or a
fixed per-Run RSS target without justification. Repetitions and an equal-policy
paired control are needed for an improvement claim; a first baseline is not an
improvement claim. Competitor arms run sequentially in rotated order, not
concurrently competing for the same resources.

## Evidence binding and host scope

Bind source commit/tree, dirty diff if any, fixture/harness hashes, build command,
actual rebuild output, executable hashes and the executed process identities.
Build source variants into separate output directories. A cached build success,
version string or source hash alone does not prove what executed. Sample raw
protocol frames and include independent expected/actual hashes. Record all
corrections and stale-artifact failures; a rebuilt pass does not erase them.

Record the operating policy, toolchain, platform, CPU/quota, memory, FD/PID/PTY
limits, devpts instance, cgroup ancestor constraints, pressure/throttling/events,
storage filesystem/capacity, host interference and owned-process census. The
[kernel cgroup v2 documentation](https://docs.kernel.org/admin-guide/cgroup-v2.html)
defines hierarchical limits; a container-local snapshot does not prove that
ancestors are unconstrained. Report incomplete host visibility explicitly.

Persistent runs include write/checkpoint/replay cost. Measure producer, live
delivery and durable fences separately. Process kill tests do not prove power
loss durability: [SQLite WAL](https://sqlite.org/wal.html) and
[synchronous policy](https://sqlite.org/pragma.html#pragma_synchronous) distinguish
checkpoint behavior, consistency and commit durability. Record actual sync
policy. File size or process I/O bytes are not an exact fsync count.

Export raw artifacts with checksums before releasing the exact owned Farm
environment. Verify cleanup of owned children, daemon and clients. Keep private
hostnames, user paths, credentials and timestamped operational receipts out of
commits; repository reports use anonymous host labels and relative evidence
references. Failure records remain available privately.

## Recorded native scale baseline

The [Run scale baseline and failure review](reviews/run-scale-baseline.md) records
the executed default and separately funded arms, including the failed persistent
soak, unexecuted frontier, resource cost and qualification gaps. Its failed
results are evidence, not replacement acceptance criteria.
