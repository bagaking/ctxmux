# Runtime defense and user configuration audit

This is a source-level audit and an accepted configuration direction. It does
not qualify runtime behavior or declare the resource or Native Features
complete. [Architecture](../architecture.md#small-user-configuration-and-owner-derived-execution-policy)
owns the boundary; [decision 019](../architecture/choices/019-resource-policy-and-honest-qualification.md)
owns current resource policy; Feature Tracker owns execution and evidence.

The [runtime policy refactor](runtime-policy-refactor.md) implements separate
sparse startup and complete exec contracts, derives observation funding from the
selected worker width, and removes `handoff_input_bytes` /
`handoff_diagnostic_bytes`. The original field census below remains historical
evidence; those two transfer quotas now belong to the original control owner.
The current advanced CLI/SDK surface has twenty-eight fields. Terminal funding
and complete recovery/scale acceptance remain open.

## Requirement and review boundary

The user requires fundamental architecture correction, examination of excessive
defense, few settings that users actually need, and prominent README guidance.
Protection is judged by the resource or semantic fact it protects and its real
failure effect. A smaller configuration surface must preserve legitimate
workload capacity, exact bytes, durable identity and truthful unknown outcomes.

The review covers serving code in the daemon, public protocol, Rust client,
CLI activation, remote transport, TypeScript SDK and the vendored terminal
dependencies. Declaration searches are supplemented by clamp/trim sites,
allocation paths, reject/retry paths and the existing incident corpus. It
distinguishes test-only constants from serving policy. Build/benchmark fixture
sizes remain historical evidence, not capacity requirements.

All thirty `ResourceLimits` fields in the original source review and their SDK counterparts are
accounted for below. Constraint families are reviewed at source level; this
is not a claim that every interleaving, host limit or allocation failure has
been executed. Existing behavioral evidence is identified separately. No new
runtime test or performance result is claimed by this documentation change.

## Current configuration and disposition

Ordinary CLI use needs no resource settings. Endpoint selection and persistence
are product choices. The ordinary optional operator choices are shared hot
replay and durable replay retention; their allowances do not bound total RSS
or all state-directory storage. Startup overrides do not reconfigure a running
Runtime, and planned exec retains its established policy.

accounts for every field, its units, owner, current pressure effect and target
disposition. These are families of controls, not thirty proven bugs. Sources:
[`resources.rs`](../../crates/ctxmux-daemon/src/resources.rs),
[`activation.ts`](../../packages/sdk/src/activation.ts) and decision 019.

## Root changes still required

The required correction is at causal owners, with these acceptance boundaries:

1. **Fund terminal derivation before allocation.** Resident history, combining
   spill, incomplete parser carry, restore/export, reflow and disk checkpoint
   work need actual owner funding. Source-level fixed limits are not a complete
   memory policy. Keep raw bytes first and prove a second real Run serves after
   each local fault. Native Feature `f-22vcz84zn/T-006` owns this open boundary.
2. **Derive execution settings without spreading fault domains.** Control,
   diagnostics, events, persistence and physical cleanup keep their own actual
   authority and progress. Transfer/encoding allowances follow admitted facts;
   no second ledger, fallback Runtime or arbitrary new ratio is justified by
   this audit. Resource Feature `f-22tcz9d9r` and the Native owner retain the
   corresponding implementation and qualification work.
3. **Reduce the configuration interface in implementation.** README now gives
   the ordinary choices. The remaining twenty-eight-field CLI/SDK surface still needs a
   source-bound reduction with validated derived alternatives and a justified
   advanced escape hatch. Renaming or hiding the same thirty knobs does not
   finish this outcome. Any genuinely necessary new control must document its
   default, units, owner, activation timing, benefit and costs in README or
   the linked advanced contract.
4. **Judge cross-owner behavior and recovery.** Use unchanged workloads and
   byte oracles, held-out geometries/fragmentation, quiet debt and a second
   real Run. Separate process exit, durable terminal confirmation, owner
   availability and applied/unknown input. Bind executed binaries to selected
   source; do not treat this static audit as a new runtime qualification.

Known historical mechanisms and their behavioral evidence are in the
[Native case study](native-owner-failure-case-study.md),
[WAL lifecycle measurement](../architecture/r19-the-wal-never-needed-to-be-empty.md)
and [persistent owner contract](../architecture.md#persistent-state-and-database-capacity).
The original P0 owner-exit trigger remains unknown. That uncertainty does not
erase the separately reproduced defects, and those defects cannot supply a
missing historical incident stack.
