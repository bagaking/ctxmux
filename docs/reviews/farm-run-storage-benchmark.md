# Farm Run 与存储 benchmark：收益和未通过场景

本轮在隔离 Farm Linux 上执行。候选源码为 `8eab24f`，对照为 `6e27fdc`；
两版使用各自的新 release 构建目录、实际编译日志与冻结执行镜像。
主分支上的 `a681942` 只增加性能记录，没有改变本轮编译输入。
[性能标准](../benchmark-standard.md)和[存储 benchmark 合同](../replay-storage-benchmark.md)
继续拥有验收条件。本报告保留失败、未执行和未知指标，不增加产品容量上限或新 SLA。

## 环境、工作量与可比范围

所有构建、测试、压测和原始字节解码均在 Farm 执行；用户要求后本机仅做
轻量编辑、Git、状态和摘要查询。本轮是一台计算节点上的普通用户隔离任务，
不是分布式集群测试。资源资金为 16 个逻辑 CPU、64 GiB 内存、无 swap、
65536 个任务与文件描述符、每个计算任务最多 7200 秒；祖先约束、主机压力和
执行身份另存私有 receipt。任务开始时主机约有 242 GiB 可用内存和 4.2 TB 可用磁盘。
这些是测试环境资金，不是 ctxmux 的产品容量或性能门槛。没有触碰用户 Runtime。

每版原矩阵有 27 个场景：memory/persistent 公共使用场景，128/512/2048/4000
真实 Run 的三轮负载，4000 Run 中 1000 路持续输出的 1800 秒负载，以及
8192 Run 默认策略 frontier。原始负载、60 秒操作观察期限、默认资源政策、
独立字节 oracle 和正常清理要求保持。已合入的事务同步改动不能代替持续负载验收。

另有三轮交错的 32 Run 对照，以对照/候选、候选/对照、对照/候选顺序执行。
短消息先取每轮八次释放的中位数；二进制输出为每 Run 262157 B 和 held-out
524311 B。该对照与未交错的大规模矩阵分开报告。大规模矩阵的分位数是
条件成功样本观察；不能平均多个 p95，也不能据此声称已得到总体尾延迟。

## 压缩几何：有收益，也有短读代价

420 个预先固定的单元：四种合成语料 × 七个几何 × 五种 codec/settings × 三轮。
几何为 128/512/1024 B、64 KiB、256 KiB、1 MiB、4 MiB；每个语料 4 MiB 加 13 B。
LZ4 1.9.4 默认、LZ4HC 默认级别 9、Zstd 1.5.4 级别 1 和默认级别 3，zlib 默认作历史对照。
140 个独立编码包按全体原始字节、部分末帧、帧内短读和跨帧范围独立解码，
累计 587204380 B。循环二进制只作强重复控制，不能代表自然输出。

下表取 256 KiB 几何的三轮中位数。压缩比只算 encoded payload；
CPU 含 Python/native 绑定、分配和复制，核对字节不在计时内。
不是生产磁盘吞吐，未计索引、wrapper、文件、WAL、垃圾和 working-space。

| 语料        | codec           | raw/encoded | 压缩 MiB/CPU-s | 解码 MiB/CPU-s |
| ----------- | --------------- | ----------: | -------------: | -------------: |
| ANSI 文本   | lz4-default     |       4.02× |          784.1 |         1156.6 |
| ANSI 文本   | lz4hc-default-9 |       5.11× |           19.4 |         2025.0 |
| ANSI 文本   | zstd-1          |      18.24× |          580.7 |         1179.7 |
| ANSI 文本   | zstd-default    |      22.36× |          447.2 |          830.2 |
| ANSI 文本   | zlib-default    |       8.54× |           29.9 |          543.0 |
| 低重复 JSON | lz4-default     |       2.63× |          536.2 |         1443.0 |
| 低重复 JSON | lz4hc-default-9 |       3.12× |           81.2 |         1119.7 |
| 低重复 JSON | zstd-1          |       5.31× |          364.7 |         1057.0 |
| 低重复 JSON | zstd-default    |       4.35× |          176.8 |          805.7 |
| 低重复 JSON | zlib-default    |       4.38× |           53.8 |          309.9 |

该 ANSI 样本上 Zstd 默认约 22.36 倍压缩、830 MiB/CPU-s 解码；级别 1 约
18.24 倍、1180 MiB/CPU-s。低重复 JSON 反而是级别 1 的压缩比更高，
所以不能预设“更高等级总是更好”。独立不可压缩样本上，LZ4 体积约增加 0.39%，
Zstd 约增加 0.006%，zlib 约增加 0.033%；raw fallback 尚未实现。
LZ4 使用块 API，不含 frame/checksum；Zstd 未启用 checksum，zlib 含 Adler32，
不能将这些载荷比当成等价的生产完整性成本。

整块解码时，一个 256 KiB 块中的 1 B 内部读取要解码 262144 B；4 MiB 块则为
4194304 B。提高分片有压缩率收益，也会增加短读成本和上下文工作集。
几何是搜索坐标，不是上线默认值。继续压缩、按时间 flush、持久化恢复、并发共享
解码和原始存储对照仍须在真实 owner 内逐项证明，才能选择生产算法和分片策略。

## 原矩阵失败

候选和对照各有 25 个完成场景、一个失败的持续场景和一个未执行的 frontier。
两版都创建了 4000 个真实子进程，并向 1000 个生产者提交原始持续工作；
所有生产者在原观察期限结束时仍未收齐预期输出。已验证前缀不能当作完整输出。
候选的 1800 次稀疏回显探测完成，但随后等待生产者时超时。

候选所有 4000 个删除操作遭持久化拒绝，报 database or disk is full，
并带有 maintenance rollback failed: cannot rollback - no transaction is active。
候选清理未报告强杀或剩余子进程；对照清理在关闭连接时遇到 BrokenPipe，
该清理保持未验收。原矩阵随后按预先声明的清理安全规则停止，frontier 保持
blocked_precondition。另起的私有 frontier 只拥有自己的证据身份，不能替换这一结果。

候选失败目录主数据库为 402489344 B，最后已提交 WAL 的数据库长度为
98285 页，接近默认 98304 页、384 MiB 的 max_page_count；当时磁盘仍有约
4.2 TB 可用空间。这支持内部数据库预算压力的诊断，不支持“主机磁盘已满”。
SQL apply 错误后的自动回滚处理与 COMMIT 结果分类是两个不同路径；
既有 COMMIT 反例通过，不能证明 apply 路径也已修复。

后续修复需要控制细碎 replay 索引的长期增长，保留已提交字节，并正确区分
确定回滚、未知提交和预算压力。数据库压力下的终止、删除和第二个 Run 可用性
需要公共行为反例。不能直接增大预算或延长观察期限后把原失败改写为通过。
吞吐不足还须区分 Native/persistence 工作、子进程定时误差及观察器成本，
当前证据不足以把所有未收齐字节都归因于同一个故障。

## 验证边界和测试修正

原始四份公共 scene 的 1456539497 B 记录范围和 fixture 输出哈希独立重建。
真实 SDK、CLI、两个 Run、输入结果、Ctrl+C、重连、planned exec 和冷历史恢复
各保留消费方 oracle。旧全矩阵 trace 缺少 fanout 连接标识，不能独立归属每个
Client 的连续流；最终 View.close 还会在主动断连后记录 EOF。因此这些字节检查
不能从最终缓存的 view facts 推导 owner 可用性，也不能抹掉未知。
新读取补测使用每条读取的独立 probe 标识，才能独立检查 2460 条流。
失败 soak 的独立前缀复核仍未完成逐 Client 归属，原始范围和全部失败原件保留；
对照还有一份 live_event_pressure Gap，不将缺失后缀称为已验证。

原候选库检查为 355 项通过、7 项旧默认保留窗口假设失败。
这七项现在显式配置历史 4 MiB 回归政策，保留 4 MiB 加 1 B、8 MiB 和原始精确
字节/游标断言；它们不再约束生产默认容量。自然退出后读历史的 helper 只在
核实同一 Run 的 Exited 状态后接受终止 attachment；活跃或 Interrupted 断连仍失败。
另一项 preflight fixture 改为实际 Run 异步 Resize admission，在原有两秒期限内
必须返回真实 applied_size，不能把短暂未获锁当成已丢失 PTY。
测试专属源变体与原生产镜像分开构建、记录实际编译和执行映像；所有前次失败保留。
修正提交 `da14508` 的两个 cfg(test) 文件与 Farm 选择的完整 blob 哈希一致；
格式、严格 Clippy 与全部 362 项 daemon 库测试通过。原生产矩阵和全仓检查仍保持失败。

## 构建和验证失败保留

首次工具复制展开了 npm 的符号链接，模块解析失败；两版真实 release 编译
已经完成，其日志和镜像哈希保留。修复的是任务专属工具布局，没有重新选择源码。
一次重复公共 probe 因既有输出目录而失败；此前实际候选和对照公共包各自有结果，
不能把重复调用失败抹掉。补测第一次因隔离环境缺失 systemd 用户总线连接而在
开始测量前退出，该失败同样保留。

全仓检查报告 Node 167 项中 160 项通过、7 项失败，core 未到最终完成边界。
失败包含产品模块覆盖率清单遗漏、冻结 qualification policy 与当前政策哈希
不一致，以及 RSS sampler 测试默认构建路径与隔离 target 不一致。
没有降低覆盖率 floor、更新冻结 policy pin 或删除测试来取得通过。
在源码专属默认 target 的 sampler 补验，只能证明修正调用环境后的该路径。

## 下一轮的因果修复顺序

1. 修复 SQLite apply-error 自动回滚分类，保留原有错误和已提交历史；以真实 FULL
   反例证明 Stop、Remove、第二个 Run 和重启事实，不能靠重启用户 Run 过关。
2. 减少长期细碎 replay 索引增长，检查 WAL、整目录、清理/compaction 峰值。
   原 4000 Run、1000 输出流、1800 秒默认政策负载必须原样再验，不直接加预算掩盖失败。
3. 改进观察器：逐连接 trace 身份和明确的主动关闭/异常 EOF，减少昂贵的全 procfs 扫描，
   独立量化 observer 有/无时的干扰。保留同样数量的 Run 和全部字节 oracle。
4. 以 raw owner 为对照实现压缩候选，同时比较 Zstd 默认和级别 1、raw fallback、
   小写入继续 flush、短尾读取和共享解码。按时间 durable 不得等分片填满，
   idle Run 不得预留整个压缩块或上下文。算法和几何由全维度行为选择。
5. 完成全仓覆盖率和 policy pin 的因果核对、生产压缩故障/恢复及使用验收，
   保持 P0 和 AgentMux 消费验收独立。一次局部提速不能关闭这些任务。

## 证据与剩余边界

私有证据拥有独立源码 bundle、实际编译日志、冻结镜像、预注册矩阵、
原始公共 frames、操作结果、资源轨迹、失败状态和回收身份。
原件直接从计算节点送到 Farm 的稳定私有归档，独立检查全部 archive member
的 SHA 后才释放精确任务身份；大文件和批量解码不经过用户本机。

生产压缩、继续帧的 durable flush、未知提交/损坏下的压缩恢复、物理断电、
OS 冷缓存、跨版本 exec、Remote/Level B 和 AgentMux 实际 GUI 使用验收
仍各有自己的边界。几何实验不交付压缩实现，也不关闭这些任务。
