# P0：持久化停滞、升级拒绝与随后历史回退

本文前半记录协议 21 时期的历史现场：旧 daemon 仍持有 Native PTY，原始输出继续增长，输入服务报告 open，但持久化输出位置停止前进。调查没有向用户 Run 发送测试输入，不能据此代签所有输入操作均可用。当时的交付尝试没有交付新协议。后续发现运行实例已改变，原任务中断且公开历史回退，见下节；旧采样不能冒充新版当前状态。该事故必须与早先 Native 输出 owner 退出、以及大规模持续负载未完成区分；它们不能仅凭相似界面症状合并成一个已确认根因。

## 后续只读复核：原任务没有无损延续

后续公开协议复核已是 generation 22，daemon 实例与原实例不同，逻辑 `runtimeId` 仍相同。当前列出 57 个 Run，其中 21 个 running；原来的 34 个 Run 记录均还在，但原来 30 个 running Run 全部显示 `interrupted / daemon_restart`，没有原 PID 继续以 running 列出。这个事实不等于已经证明所有旧子进程实际死亡，更不代表新任务承接了原任务的隐藏进程状态。

23 个原 Run 的公开输出 head 低于先前采样位置。当前历史记录不能提供先前已观察到的完整输出，输入 applied 事实也不能从历史恢复中补造；不能仅凭相同逻辑 Runtime 身份或 Run 记录仍存在声明无损恢复。尚未确认其他客户端或存储是否保存了缺失部分，不能把公开历史缺口直接换算成已证明永久丢失的字节。

该次底层切换的触发来源尚未查清。ctxmux 调查方与接入方均未执行此次切换；实际进程带有 handoff 参数也不能证明原 PTY、输入和全部字节连续。接入方后续 App 更新保持的是当时已存在的新运行实例，不是对原 30 个任务恢复的验收。

新的两轮只读采样间没有输出或 durable 位置变化，不能据此认定当前 21 个 running Run 的持久化也已故障：采样没有证明这些任务期间产生了新输出。调查没有向用户 Run 发送输入、信号、恢复或数据库修改请求。旧事故、当前服务状态、切换来源和历史连续性分别保留证据，完整恢复验收仍未通过。

## 已确认事实

运行镜像为 `b061b8d`、协议 generation 21。保留构建的完整文件哈希、加载镜像 UUID 和内核代码身份相互核对；这不是从当前安装路径反推仍在运行的镜像。

公开旧 SDK 返回 34 个 Native Run，其中 30 个 running、4 个 exited。138 个上层 Session 记录不是 138 个 Native Run。两轮只读采样中，5 个 Run 的原始输出累计增长 2,159,331 字节，所有 Run 的 `durable_output_bytes` 均未前进。第一轮 30 个 running Run 的累计未提交尾部为 343,450,076 字节；12 个 Run 的持久化位置已经低于其内存最早保留位置。该累计值是采样时的输出债务，不是已确认丢失的字节数量，也不是固定产品容量。

只读线程样本仍有 `ctxmux-native-owner` 在 poll/read，持久化 actor 等待命令；没有看到仍在进行的升级阻塞线程。这不能解释过去的具体拒绝原因，但不支持“当前升级仍卡在存储等待”的说法。

公开 diagnostics 报告 sink 已失败、最后错误为 `EPIPE`、writer 已退出。具体升级失败消息没有保留下来。诊断写入失败和 Run 服务必须分别报告：writer 退出不代表 PTY owner 已退出，PTY owner serving 也不代表持久化可用。

实际交付尝试后仍是协议 21。消费方恢复旧 App 并保留原 Run，没有用停止子进程或冷重启把安装步骤伪装成无损升级。

## 可以推断到哪一步

旧版本 `perform_exec_upgrade` 在提取任何 PTY 描述符之前检查 `Persistence::is_failed`；持久化失败会拒绝升级并保留原 owner。落盘位置长期停滞、输出继续前进、actor 等待新命令，与这个全局失败状态一致。因此持久化失败是有强证据支持的升级阻断解释。

但尚未取得首次持久化错误的原始内容，不能把某次 replay 冲突、SQLite 错误、磁盘不足或诊断断管指定为已经确认的首次根因。大规模 bench 中的 `cannot verify evicted replay range` 已有独立反例和修复；这些反例不能替现场补造缺失日志。

旧版本还通过 `current_exe()` 选择未来执行路径，只校验目标 handoff schema。安装路径、别名路径和加载镜像身份是不同事实。回滚后别名解析到旧镜像，不能证明发出升级信号时也指向旧镜像。当前证据没有把路径问题确认成此次升级失败的根因。

## 为什么不能直接重试或重启

旧协议没有持久化重开、修复、失败状态查询或显式升级目标的公共请求。已实现的 SIGHUP 路径在持久化失败状态下首先拒绝；它不是非停止恢复入口。另起 daemon 也不能绕过原 state owner 的锁。

已提交位置低于内存 replay floor，意味着“从当前内存重写一遍”不能证明覆盖全部未提交历史。关闭失败保护、编辑活跃 SQLite、删除状态、强杀或冷重启，都会绕过尚未满足的持久性条件。它们不能作为无损修复的验收方法。其他客户端是否另存某些字节，也必须单独核对来源、身份和完整性，不能当成已经实现的恢复能力。

## 对修复和验收的约束

持久化 owner 必须公开当前服务状态、首个失败及其分类、已接受与已提交的位置、原始字节债务和升级拒绝结果；这些事实不能依赖 stderr 的读端仍存在。`running`、静态 persistence capability 和 PTY owner serving 都不能代替这些运行期事实。

非停止恢复只能在同一个持久化 owner 下先确认原事务结果和字节来源，再讨论恢复操作。未知 COMMIT、仍可验证的重叠字节和不可补齐历史必须继续明确拒绝。没有这样的实现和实际验收时，应报告恢复入口缺失，而不是加一个盲目重试按钮。

验收需覆盖诊断 sink 先失效、真实持久化故障、第二个仍服务的 Run、两个公开 Client、输入 exact/unknown 结果及保留原身份的升级拒绝。已通过的两个小 Run 跨协议镜像升级，只证明那两个明确镜像与负载；不能代签具有长期输出债务的现场。大规模修复仍按[原始基准](run-scale-baseline.md)的字节、负载、观察窗口和收尾标准验收。
