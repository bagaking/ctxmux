# 大规模 Run 基线与故障复盘

本轮建立了可重复的公开协议 bench，也发现了尚未通过的生产问题。当前不能宣称“大规模能力全部验收通过”，更不能把增加预算称为性能优化。

## 范围与证据

目标是有用、可靠的 Run 容量：客户端离开后，原 Run、进程所有权、身份、字节顺序和声明的持久性仍成立。吞吐、延迟、公平性、资源、容量、恢复和使用体验必须一起考察。完整约束见 [性能标准](../benchmark-standard.md)。

基线实际运行 Rust daemon `a87c11ca`，协议 generation 22。默认策略使用同源 harness；另一个独立预算组使用 `9fb90195` harness，daemon 和 SDK 保持原有已验证构建。后者只将 `live_event_bytes` 从 64 MiB 改成 512 MiB，工作负载、字节 oracle、观察窗口和持久性要求没有改动。两组均记录源码、真实构建、执行文件哈希和进程身份。

验证环境为 Linux x86_64、Rust 1.96，计算 Job 请求 16 CPU / 32 GiB，限制 32 CPU / 64 GiB。约束、采样成本和宿主干扰均保留；这是一组观察基线，没有冻结的竞品比较噪声门槛，也没有性能提升声明。用户 Runtime 没有参与压测。

默认组 387 个原始文件，共 327,073,352 字节；独立预算组 410 个原始文件，共 2,296,124,030 字节。Root 已逐文件重新读取并核对全部 SHA-256；原始失败和源绑定保留在受控归档中，报告不公开机器路径或操作身份。

归档 SHA-256 只证明导出文件的完整性，不证明 Run 已产生或交付全部预期输出。

## 完整矩阵结果

预先选择 27 项：两个公开客户端场景，加上 memory-only / persistent 各自 128、512、2048、4000 Run 的三次重复，最后加一个 8192 Run frontier。30 分钟持续负载只属于最后一次 persistent 4000 Run；没有声称 memory-only 也完成相同持续负载。

| 组 | 已执行 | 通过 | 失败 | 未执行 |
| --- | ---: | ---: | ---: | ---: |
| 原始默认策略 | 27 | 14 | 13 | 0 |
| 独立 512 MiB 事件预算 | 26 | 25 | 1 | 1 |

默认组的 2048、4000 和 8192 Run 都成功创建了全部请求的进程，但无法为所有选定 Run 建立观察者，因而没有释放这些组的完整同时输出负载。它们是失败，不能称为该规模吞吐已通过。

根因定位到共享事件环的固定预留：每个已订阅 Run 52,224 字节，64 MiB 只能资助 1285 个环。2048 Run 的独立诊断保存了全部 2048 次建立观察者的尝试，其中 1285 成功、763 返回明确拒绝。环由同一 Run 的观察者共享，不能误算成每个 Client 一份。

512 MiB 是独立策略实验：8192 × 52,224 = 427,819,008 字节，再选择可以资助这些环及场景余量的二进制预算。它解释了原始拒绝，却没有证明固定 256 个事件槽的设计合理，也没有消除其必须优化的预留成本。默认失败仍保留。

原完整组收尾后，独立 Runtime 已补测相同策略下的 memory-only 8192 Run：两个所选单元均通过，包含公开客户端场景和完整 active / mixed fleet，全部 8192 个 Run 停止并删除。补测使用 `fdd4da4a` harness 和原始 `a87c11ca` daemon；新增 harness 只保存清理前证据。43 个原始文件、67,411,999 字节全部重新读取并核对 SHA-256。daemon 最大观察 RSS 为 2.51 GiB，Start 成功样本 n=8192、p95 为 170.5 ms；最大资源观察间隔 7.07 秒。它证明该特定短负载和策略，没有改签原完整组的 blocked 项，也不证明 8192 Run 的持续负载或 persistent 模式。

## 持续负载为什么失败

4000 个真实 Run 中，1000 个持续输出 ANSI token，另一个安静 Run 接受每秒一次的输入输出探针。1800 次探针全部完成。但最终 1000 个持续输出流都没有收齐：校验了 695,090,406 字节，距预先生成的完整预期还差 368,467,644 字节，最终等待超时。

这部分数据是“尚未完成并验证的输出”，不能直接写成“已产生但丢失的字节”。现有证据没有证明所有预期字节都已由子进程产生。已观察的这些流没有字节错配或 Gap；完整流仍未通过。

收尾尝试了全部 4000 个 Stop：3032 完成，968 返回明确 unknown，原因是物理停止后终态发布或 Native entry 退休尚未完成。3032 次 Remove 全部失败，其中 2965 为持久化拒绝，67 为未满足删除条件。最终没有遗留 fixture 子进程，也没有强杀 benchmark daemon；这不能抵消失败的终态和删除结果。8192 项随后因清理前提不成立而明确记为未执行，另行补测也不会把原始组改成通过。

持久化失败记录包含 `cannot verify evicted replay range`。源代码中的完整终态 replay、已提交 watermark、全局历史回收和严格重叠校验需要一起检查。应修复内部已确认字节的所有权和先后关系，同时保留对改变字节、可恢复缺口及未知 COMMIT 的严格拒绝；不能删掉校验来消除错误。

故障期间实际 PTY 输出 owner 存在，八个终态处理线程等待持久化处理。两秒 CPU 采样显示 SQLite 遍历、缓存和读取成本，没有可信的 Rust 调用链，因此只能定位到存储处理路径，尚不能据此认定某条 SQL 或 compaction 是全部根因。这与先前“输出 owner 已退出”的 P00 故障不是同一条已证实的因果链。

## 资源与延迟

短负载下，daemon 的最大观察 RSS 如下。每行保留三次重复的范围；持续负载单独列出，不混进短负载平均值。

| Run 数 | memory-only RSS | persistent 短负载 RSS | Start 成功样本 p95，memory-only | Start 成功样本 p95，persistent |
| ---: | ---: | ---: | ---: | ---: |
| 128 | 45.7–46.0 MiB | 47.0–47.7 MiB | 17.6–39.2 ms | 33.0–33.8 ms |
| 512 | 163.3–166.8 MiB | 168.9–170.0 MiB | 22.8–24.1 ms | 34.1–37.4 ms |
| 2048 | 647.9–648.5 MiB | 651.3–653.7 MiB | 54.1–56.0 ms | 62.4–84.2 ms |
| 4000 | 1257.9–1259.2 MiB | 1264.8–1264.9 MiB | 91.9–94.6 ms | 104.6–114.3 ms |

Start 为并发度 8 的闭环请求，每次重复的样本量等于 Run 数。这些是成功请求的样本分位数，不能外推总体尾延迟或产品 SLA。

持续负载中，daemon 最大观察 RSS 为 33.14 GiB，generator 为 3.49 GiB，recorder 约 11.9 MiB；fixture 和内核资源还要另计。终端模型固定保留 10,000 行的密集单元状态，与热字节和事件预算分开，构成需要修复的内存成本。不能把减少终端保真度或少创建 Run 当成内存优化。

1800 个探针成功样本的 p50 / p95 / p99 为 635.4 / 1469.6 / 1937.6 ms，最大 3461.4 ms。这证明服务仍有响应，也暴露了明显成本，不能简写成“探针全部成功，所以可用性良好”。

资源轨迹有 1131 次采样，最长采样耗时 31.19 秒，最大相邻观察间隔 32.40 秒。上述内存数据是最大观察值，不能声称精确峰值。采样自身的 CPU、内存和延迟属于测量成本，不能隐去。混合阶段旧 harness 还把安静 Run 的空操作计入 `arm_mixed`；该分位数不能代表真实建立观察者或发送输入的延迟。

## 已修复与剩余验收

Linux 升级候选修复了启动安装路径和执行镜像的所有权：预检与实际 exec 使用同一个保留的镜像描述符，原路径保留为安装路由。七个真实双 Run / 双 Client 用例覆盖绝对路径替换、相对目录重建、PATH 符号链接、预检期间删除、两种伪造 argv0，以及提取前拒绝缺失镜像。仅修路径而不保留镜像的反例会在提取后 exec 失败。候选通过 Linux 339 个 library tests、63 个 native lifecycle tests 和静态检查；owner 故障及 Stop 精确前缀各重复三次。它们不证明不同协议 generation 的升级。

macOS 新构建的四个公开 CLI / SDK 小规模场景通过。另一次完整本机单元测试遇到真实磁盘不足并失败，原始记录保留；不能将其写成完整 macOS 回归通过。非 Linux 的镜像替换竞态仍需独立验收。

bench 已将完成的工作负载、字节 oracle 和延迟在清理前保存，并明确留下“清理未验收”。这个修复防止 Stop 卡住时丢失完整结果，不会替产品通过生命周期验收。

后续已用两个独立确定性反例复现持久化错误：终态 replay 跨过已回收的提交前缀，以及终态提交超过本 Run 已接受的排队输出。候选先提交该 Run 的已接受前缀，再处理终态尾部；只省略已经确认且已回收的前缀，保留对仍在存储中的重叠字节的校验。第一版还触发了原有等待预算回归，失败记录保留；修正后 macOS 的 80 项持久化测试通过，包括字节变更拒绝和未知提交结果的原有门槛。两个真实 Run、两个公开协议 Client 的补测通过输入输出、Ctrl+C、Stop、Remove 及已退出历史的冷恢复。冷恢复保留原 PID 作为历史身份，并公开历史 owner 已停止，不能据此宣称活进程被重新接管。这些小反例和验证不证明原持续负载已通过。

终端成本候选把每个 Cell 的颜色/样式表示从两个带 padding 的枚举换成完整 RGB 字节与明确的语义位，Cell 实测从 40 字节降到 32 字节，历史行数、Unicode、宽字和声明的颜色能力保持。公开 SGR 测试覆盖所有 indexed 颜色、独立样式、RGB 各分量与默认复位。相同 macOS 进程样本各三次、8 个模型、80 列、10,000 行历史：原实现 RSS 329,376–329,408 KiB，候选 222,032–222,048 KiB。它是派生模型的单独成本观察，不能外推 Linux、完整 Run 或 4,000 Run 性能提升；原始 Linux RSS 采样器在 macOS 返回 unavailable 的第一次结果也保留。

相同新构建的 macOS 组合候选通过 80 项持久化回归和四组公开 CLI/SDK 小规模单元，静态检查通过。独立 xterm 的七个真实生成样本在原表示与紧凑表示间完全相同，恢复状态、模式和后续原始字节都严格一致；额外可见字符的负例被拒绝。旧验收脚本强制要求出现一个已不存在的差异，因此先失败；现改为七例都精确相等，原失败保留。这是修正历史实现刻画，不能据此宣称全部 codec 或客户端能力通过。

组合候选已完成 Linux 源码、实际构建及冻结执行镜像绑定：342 项 library tests、63 项 native lifecycle tests、17 项 codec tests、6 项真实终端 owner tests、七个独立 xterm 样本通过。两个不同执行镜像的双 Run / 双 Client 升级场景通过，保持原 daemon PID、listener inode、Run/PID、输入游标和已结算输入结果，并核对完整后续字节、Ctrl+C 与重连。它们同为协议 generation 22，不代表跨协议 generation 升级。旧 `b061` / generation 21 owner 在安装路径替换后的两种反例仍未具备升级资格，但原双 Run 保持可用；仅更新 incoming 镜像不能修复旧 outgoing owner 的目标选择。用户现有 Runtime 没有被重启或替换。持久化双 Run 收尾及冷历史恢复、四组公开 CLI/SDK 单元通过；171 个原始文件、210,158,749 字节完成独立重新读取及 SHA-256 核对。静态检查通过，但保留前台观察模块两条平台条件 import 警告。此前一轮最终导出遇到控制面 SSH 传输失败和 Pod 到期，原始结果未成功导出；该轮不计为通过。新一轮还保留验收 target 名错误、错误依赖前一轮已清理的测试目录，以及测试构建覆盖 release 输出后被镜像哈希校验拒绝的失败。最终使用独立新输出重新构建并冻结公开验收镜像；所有实际用例、字节 oracle 和用例等待预算保持，没有改签失败记录。

接下来按独立 owner 完成：

1. 将已验证的修复和源绑定证据交给消费方；保存原始失败及独立评审的支持、未证实和被拒绝结论。
2. 查清持续输出背压及 SQLite 扫描成本，保留同样的 1000 个输出流、全部预期字节和原观察窗口，重新执行持续负载及收尾。
3. 修复事件环固定预留和终端历史密集存储的成本，明确预算、压力和保真度；匹配原始负载，核对所有受影响性能维度。
4. 保留独立 8192 Run 与原组未执行项的不同身份；改进采样覆盖和真实操作分母。
5. 后续资源 owner 改动完成后，对最终组合重新绑定源码、执行镜像和完整负载；当前已完成的不同执行镜像升级不能代签未来改动。AgentMux 的实际 GUI 使用验收由消费方完成，不能从本报告的 CLI / SDK 推断。

Gemini 调研及挑战已经用于完善标准。Root 独立核对了来源、执行和失败；两个后续 peer 曾读取声明边界外的包清单，相关边界门未通过，没有把它们的自报 PASS 当成独立验收。新故障的有界审查继续保留实际读取、来源及未证实项。
