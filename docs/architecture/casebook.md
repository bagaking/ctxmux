# Architecture wrong-case casebook

This casebook turns external failures into ctxmux-specific test obligations. The evidence source of truth is the [research topic](../../.bagakit/researcher/topics/engineering/ctxmux-wrong-case-corpus/index.md); the architecture records keep only the decision-facing synthesis.

## Dispositions

- `covered`: an existing continuous test already proves the transferred invariant.
- `active`: the capability exists and T-010 must run an executable fixture continuously.
- `characterization`: the behavior exists but the contract is unresolved; record reality without freezing it as the desired invariant.
- `future`: the owning capability or deterministic test seam does not exist. The activation task is explicit.
- `rejected`: the external case does not belong to the ctxmux core oracle.

Fixture status never upgrades an external source into proof. The fixture must reproduce the ctxmux failure mechanism and assert public behavior.

## Continuous-test handoff

T-010 materializes this table as one machine-readable corpus rather than a second orchestration framework. Every row will carry its choice, source ids, failure mechanism, invariant, platform, disposition, activation task, and test reference. Active and covered rows must point to checked-in evidence; future rows must name the capability task that activates them.

The casebook is complete when every retained case has a fixture disposition. The runtime is mature when every applicable case has executable public-behavior proof.
